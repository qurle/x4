# Logging

Owner requirement: *clean structured logs*. One module (`shared/include/x4/log.h`), one format,
identical on the Core and the cameras. No `Serial.print` anywhere in x4 code; ESP-IDF/library
`ESP_LOGx` output is captured and re-emitted in the same format (`mod=idf`).

## Format (logfmt)

```
t=12345 lvl=INFO dev=core mod=net evt=register cam=2 ip=192.168.4.12 fw=0.1.0
│       │        │        │       │            └ free key=value pairs (no spaces in values)
│       │        │        │       └ event: stable snake_case name — grep for this
│       │        │        └ module: boot power flash cfg sd ui input net xfer shoot preview web ota cam http bench therm sys idf
│       │        └ device: core, cam1..cam4 (cam? = id not set)
│       └ ERROR WARN INFO DEBUG TRACE
└ uptime in ms of the device that wrote the line
```

- Errors carry a code: `err=300 err_name=SD_MOUNT_FAIL` (catalogue below).
- Values never contain spaces; text is sanitised (`sanitizeValue`): spaces → `_`, quotes/`=` removed.
- Max line 240 bytes; longer lines end with `~`.
- Rate-limited call sites append `dropped=N` (how many identical events were suppressed).
- Camera WARN+ lines are forwarded to the Core over UDP and appear in the Core's log unchanged
  (their own `t=` and `dev=camN`), so one serial port on the Core shows the whole rig.

Why logfmt and not JSON lines: shorter on a 115200-baud console, readable by eye, trivially
parsed (`tools/x4log.py`), and the same `key=value` grammar is used by the UDP protocol.

## Levels

| level | use for | examples |
|---|---|---|
| ERROR | something failed and needs attention | SD mount fail, sensor mismatch, flash watchdog |
| WARN | degraded but working, or a safety guard acted | clamped config, camera offline, slow transfer |
| INFO | one line per meaningful event | boot banner, register, shot start/ack/stored |
| DEBUG | detail for one subsystem | input actions, per-frame bench lines |
| TRACE | per-packet | heartbeats |

Compile-time ceiling `X4_LOG_COMPILE_LEVEL` (default 4 = TRACE compiled in); runtime level
`log_level` (default 2 = INFO), changeable live from the web page. Cameras forward lines at
`log_fwd_level` or worse (default WARN).

## Sinks

| sink | Core | camera | notes |
|---|---|---|---|
| serial (USB CDC 115200) | ✔ | ✔ | zero TX timeout: never blocks when no USB host is attached |
| RAM ring | 128 lines | 64 lines | Core: diagnostics screen tail + `GET /logs?since=<seq>`; camera: `GET /logs` |
| SD file | optional (`log_sd=1`) | – | `/x4/logs/x4.log`, rotates to `x4.1.log` at `log_sd_max_kb`; written by the loop, never by the caller |
| forward to Core | – | ✔ (WARN+) | UDP `X4/1 LOG cam=N <line>` |

Performance rules: the formatter uses stack buffers (no heap), the SD sink only enqueues, nothing
logs from ISRs or the LVGL flush callback, hot paths use `X4_LOG_EVERY(ms, …)`.

## Boot banner

Every boot prints, in order: `boot/start`, `power/state` (the 5 V output assertion), `boot/banner`
(fw, git hash, build time, protocol), `boot/chip` (chip rev, CPU MHz, flash, PSRAM, MAC, board),
`boot/reset` (reason, boot counter, brown-out counter), `boot/memory`, `cfg/loaded`,
`cfg/summary part=N` (the full active config), then one line per subsystem init.

## Module / event catalogue (main events)

| mod | evt | meaning |
|---|---|---|
| boot | start, banner, chip, reset, memory, ready, stagger | boot sequence |
| power | state, assert | 5 V output state; `assert` only on problems |
| flash | init, armed, fire, refused, watchdog | flash guard decisions |
| cfg | loaded, summary, set, clamped, migrate, applied, reset | configuration |
| sd | mount, bench, write, full | storage |
| net | ap, udp, register, register_info, cam_online, cam_offline, hb, shoot_sent, joined, lost, registered | network |
| shoot | start, refused, ack, captured, stored, slow, unscheduled | shooting flow |
| xfer | init, done, fail | photo transfer (`ms`, `kBps`) |
| cam | sensor, hw_rev, res, held_dropped, held_expired, frame_bad, init | camera sensor |
| bench | start, size, frame, done | camera Stage 0 benchmark |
| http | start, shot_sent, stream_start, stream_end | camera HTTP |
| ui | lvgl_init, begin, screen, replay, touch_test, preview_decode | UI |
| therm | warn, ok, throttle, recovered | temperature |
| web | start, action | Core web server |
| ota | ready, start, end, error, disabled | OTA |
| idf | `<tag>` / log | captured ESP-IDF/library messages |

## Reading logs

Live, as a table:
```bash
cd core && pio device monitor -e core | python ../tools/x4log.py
```
Only problems, from a saved file:
```bash
python tools/x4log.py core.log --lvl WARN
```
One subsystem, chosen columns:
```bash
python tools/x4log.py core.log --mod shoot,xfer --cols t,dev,evt,shot,cam,bytes,ms,kBps
```
Per-shot timing summary (skew, captured, total, per-camera transfer):
```bash
python tools/x4log.py core.log --shots
```
Error histogram straight from the rig:
```bash
curl -s http://192.168.4.1/logs | python tools/x4log.py --errors
```
CSV for a spreadsheet: add `--csv`. `grep` works too: `grep 'evt=stored' core.log`.

Debugging workflow: start with `--lvl WARN`, find the first `err=`, look it up in the table above,
then filter that module at DEBUG (`log_level=3` on the web page) and reproduce.
